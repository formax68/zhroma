<objective>
Close **WR-02** and **WR-05**: pin the worker's boundary validation and the completeness of the
finite diagnosis protocol, before the taxonomy grows.

Purpose: three surviving mutants show the worker's reply boundary is unspecified — deleting
`reply.requestId === requestId`, replacing the entire shape-and-diagnosis gate with a constant, and
deleting the `Object.hasOwn(TITLES, …)` pairing clause each leave the suite green. So does deleting
the popup's own `validStatus` / `validPreference` gate and its unknown-key fallback. The property
`04-VALIDATION.md` names as `requestApply`'s *only* staleness key is therefore unprotected in the
removal direction: the suite catches the wrong guard being **added** but not the right one being
taken **away**.

The pairing clause matters most. `TITLES` is keyed by the whole pair while `ICONS` is keyed by status
alone, so an unpaired combination that gets past the gate produces a toolbar carrying one state's
artwork under another state's title — or, in Chrome, a rejected `setIcon` whose `catch` swallows the
error so `setTitle` is never reached and the tab keeps its previous claim about the view. That is the
failure mode FAIL-05 exists to prevent, and taxonomy growth means editing `DIAGNOSES`, `REASONS`,
`ICONS`, `TITLES` and the popup's `COPY` in five places with nothing asserting they stay in
agreement.

Output: one test per clause, a structural completeness assertion over the whole product set, an
action double that refuses an unknown icon path the way Chrome does, and mutants that each must die.

Reference: `04-REVIEW.md` → WR-02, WR-05, and `## Required judgment 1` group C.
</objective>

<how_to_produce_an_illegal_reply>
The real `extension/content.js` cannot produce an out-of-set diagnosis, an unpaired pair or a wrong
request id — that is the point of it. The hazard is therefore constructed with a **hand-registered
content listener**, using the seam the tracer already exports and adding no new harness mode:

`world.contentChromeFor(tabId).runtime.onMessage.addListener(listener)` pushes onto the same
per-tab listener list `loadContent` uses, so a test can answer the worker's `get-status` and
`apply-preference` requests directly with any payload it likes, without loading the real content
script into that tab. That is what makes every clause in `validDiagnosis` and `isExact` reachable.

Where a test needs a *legitimate* prior state to go stale — the pairing-clause behavioural test does —
load the real content script first, let it establish `working`, then register the rogue listener for
the following exchange.
</how_to_produce_an_illegal_reply>

<harness_fidelity_note>
The tracer's action double currently accepts any `path` and records it, so an out-of-set status
produces an `actionLog` entry with an undefined icon rather than Chrome's rejection. Task 2 closes
that gap so the double models the platform: an icon path outside the packaged inventory is refused.

Until it does, the observable for a bypassed pairing clause is a **wrong** toolbar rather than a
**stale** one. Both are red tests, so the coverage is real either way — but the fidelity fix is worth
making, because the review's stated impact ("the tab keeps the previous icon and title") is only
reproducible once the double rejects like Chrome.
</harness_fidelity_note>
