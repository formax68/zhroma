<the_discriminating_observation>
The review's fix note suggests flushing the two deferred writes **in reverse order** and asserting
the last request still wins. That would need a new reverse-flush control on the tracer, and
`test/extension/tracer-world.js` is owned by 04-13 in this same wave.

A stronger observation is available with the controls that already exist, and it observes the property
directly rather than through a consequence of it:

> **With the queue present, at most one preference write is ever in flight.**

Traced through the shipped code with `writeMode: 'deferred'`:

- **Queue present.** The first request's task calls `chrome.storage.local.set`, whose promise never
  resolves until flushed, so the task parks. The second request is chained onto the queue behind that
  parked promise, so its `set` is **never called**. `pendingWriteCount()` is **1**.
- **Queue collapsed** to a bare call. Both tasks start immediately, both call `set`, and
  `pendingWriteCount()` is **2**.

So the count alone discriminates the mutant, needs no new control, and states the single-writer rule
as an invariant instead of inferring it from a final value that happens to be the same either way.
The arrival-order and last-request-wins assertions are then checked by flushing stepwise: flush,
observe the first commit and the second write appearing, flush again, observe the final stored value.
</the_discriminating_observation>

<closed_tab_cleanup_constraint>
The `tabs` map has **no external observable**. Its only consumer, `stateFor`, creates a fresh entry
for an unknown tab id, so a leaked entry and a cleaned one are behaviourally identical: a reused id
gets a generation that no held reply matches in either case. The map's size is not reachable from the
double.

Exposing a count or a projection tally from the worker would change a shipped byte, which would
re-invalidate the acceptance binding 04-11 has just re-established and require a second full
re-establishment for a test-only affordance.

That is a **constraint**, not a judgment about difficulty. The cleanup is therefore guarded by a
**source-shape assertion** — the project's own idiom, already used in this same suite for the
storage-method allowlist, the icon inventory and the absent lifecycle listeners. The plan states this
plainly rather than claiming behavioural coverage it does not have, and pairs it with the behavioural
assertions that *are* available: closing one tab does not disturb another tab's toolbar, and a
projection for a closed tab neither throws nor paints.
</closed_tab_cleanup_constraint>
