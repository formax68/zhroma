<objective>
Re-establish the Phase 4 acceptance record against the bytes that now ship, and close the missing
04-05 completion record.

Purpose: 04-07, 04-08 and 04-10 changed four of the eleven shipped assets, and 04-09 changed the
timing harness. `04-VALIDATION.md` promotion rule 3 is explicit — any change to any of the eleven
shipped assets invalidates the binding and therefore invalidates promotion; the record must be
re-established against the new bytes, not re-pointed at them. `04-LIVE-ACCEPTANCE.md` rule 5 says
the same thing in the operator's voice: any source change invalidates the run, preserve what was
observed so far as history, and never re-point an old observation at new bytes. And
`test/extension/phase-04-live-acceptance.test.js` enforces it mechanically at the
`live-source-evidence` gate: a check may leave `pending` only when `loaded_from_repository` is true,
and that branch requires a `source_confirmed_on` and a fully populated `environment` for the bytes
in the tree — so no edit to the record alone can produce a pass until somebody re-confirms the
current bytes in a browser. The record currently asserts a binding to bytes that no longer exist,
and its byte pin has been red since wave 7.

Output: the pre-repair records preserved verbatim as history; fresh timing samples on final source;
an acceptance record whose hashes match the shipped bytes, whose checks all read pending, and whose
disposition is computed as `human_needed`; a dated AR-04-01 addendum; and `04-05-SUMMARY.md`.

Reference: `04-VALIDATION.md` promotion rules; `04-REVIEW.md` CR-01's fix note
("Re-bind the acceptance record afterwards"); `04-RISK-ACCEPTANCE.md` AR-04-01.
</objective>

<consequence_notice>
**This plan resets fourteen user-attested live passes to pending, and that is the correct outcome.**
It is stated here rather than buried in a task body because it is the most consequential thing in
the run.

Those fourteen observations were taken on 2026-09-10 against the pre-repair bytes. Three mechanisms
make it structurally impossible to carry them onto the repaired bytes: `04-VALIDATION.md` promotion
rule 3, which invalidates the binding and therefore promotion on any change to any of the eleven
shipped assets; `04-LIVE-ACCEPTANCE.md` rule 5, which says to preserve what was observed as history
and never re-point an old observation at new bytes; and the validator's `live-source-evidence` gate,
which lets a check leave `pending` only when `loaded_from_repository` is true — a state reachable
only by re-confirming the bytes now in the tree. The validator's `observation-date` gate is
deliberately **not** cited among them: it only requires `observed_on` to be no earlier than
`source_confirmed_on`, which a same-day re-confirmation would satisfy, so it is not the mechanism
that stops the carry-over. An observation is evidence about the bytes it was taken on, and no amount
of record editing transfers it. The fourteen are preserved verbatim, with their user attributions, in
the history directory Task 1 creates. Re-observing them is a **UAT** activity and is out of scope for
this run.

**The user is told, not asked — through a path that exists.** The reset is mandated by the three
mechanisms above, so nothing here is a permission gate; but the person who attested those fourteen
observations is owed the news. Under this project's `workflow.human_verify_mode: end-of-phase`,
`checkpoint:human-verify` tasks are suppressed, and the sanctioned route is the human-check block
inside Task 3's verify step: the verifier harvests it at end of phase, which forces the phase
disposition to
`human_needed` and consolidates the acknowledgement into `04-UAT.md` for the user to read in one
batch. That is why this plan stays `autonomous: true` and emits no checkpoint task. Task 3 also
records the request as `ACK-04-01` in `04-VALIDATION.md`, so the outstanding acknowledgement exists
as a repository artifact and not only as a harvested prompt.

What this plan does **not** do:

- It does **not** flip `language-icon-copy` or `structure-copy` to pass. They were never observed,
  they stay pending, and **AR-04-01 stands unchanged**.
- It does **not** plan or perform any work to manufacture a non-English tenant or an uninterpretable
  table. That is explicitly out of scope for this run.
- It does **not** promote the three ratified prohibition judgments out of flagged-unverified. The
  test asserts the repository record carries all three that way as a guard against an executor
  self-ratifying them, and relaxing that guard is a user decision, not a side effect of re-binding.
- It does **not** delete or rewrite the previous records. They move to history alongside a note
  saying what they do and do not validate.
</consequence_notice>
