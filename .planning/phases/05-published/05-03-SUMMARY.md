## Decisions Made

- **Pin the revisions in the baseline; do not re-derive them at test time.** The revisions were derived from `git log` before any shipped byte moved, exactly as the plan requires, and then written down. Re-deriving on every run would make the evidence move whenever someone touched the file for an unrelated reason; pinning makes that touch a failure instead.
- **Identify the original validator from Git, but do not compare it to disk.** This plan is editing that file. Recording which validator produced the verdict is honest; asserting the same file is still on disk unchanged would be a contradiction.
- **Pin the auxiliary evidence in both directions.** `validateWorkloadReport` — the code that judges the historical timing samples — is imported from the working copy, so if the harness changed, the historical verdict could shift without anyone noticing. Both harness files and all seven evidence documents are therefore held against their committed bytes.
- **Keep `manifest.version` at `0.1.0`.** The store rejects a re-upload with an unchanged version, but nothing has been uploaded. Bumping it now would fabricate a release history; it changes when an actual upload requires it, and that change produces fresh candidate and smoke evidence.
- **Read the four hues out of `zhroma.css` rather than transcribing them.** The brand accent is the product's own palette by construction, so a future palette change cannot leave the mark quietly stale.
- **Assert what a test can settle and no more.** Dimensions, PNG form, the transparent margin and the presence of all four hues are machine-checkable. Whether the mark is legible and looks right is not, and is left as an explicit human judgment.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] A RED control forbade the literal `extension/`, which the adapter cannot avoid**

- **Found during:** Task 1 (GREEN phase)
- **Issue:** The RED commit expressed "the adapter must not read the working tree" as `expect(adapter).not.toMatch(/extension\//)`. But the adapter has to build Git paths of the form `extension/<name>` to read the historical blobs at all, so the only way to satisfy that assertion was to assemble the string from fragments — obfuscation that would have made the file harder to review while proving nothing.
- **Fix:** Replaced the textual ban with a behavioural guard plus a tighter textual pin. `readWorkingCopy()` now refuses any path inside the shipped tree and is exercised directly (`extension/manifest.json` and `extension/icons/brand.png` both throw `phase-04-runtime-source-read`), and the test pins that exactly one `readFileSync` call exists in the whole adapter — the one behind that guard. The no-fallback patterns (`catch { return readFileSync`, `|| readFileSync`) remain banned textually.
- **Files modified:** `scripts/phase-04-source.js`, `test/extension/phase-04-live-acceptance.test.js`
- **Verification:** the control fails if the guard is removed, and it now proves refusal rather than absence of a substring.
- **Committed in:** `4a013ff` (Task 1 GREEN commit)

**2. [Rule 3 - Blocking] Two further test files independently pin the shipped inventory**

- **Found during:** Task 2
- **Issue:** The plan's `files_modified` named `runtime-contract.test.js` as the place the inventory is pinned, but `toolbar-popup.test.js` pins the icon directory and `manifest.icons` separately, and `release-package.test.js` asserts an eleven-asset count twice. Adding a twelfth shipped file left all three failing. Leaving any of them stale would have broken the invariant that a new shipped byte and every inventory that describes it move in one reviewed commit.
- **Fix:** Moved all of them to the twelve-file set in the same commit as `brand.png`, and strengthened rather than relaxed them: `toolbar-popup.test.js` now asserts `manifest.icons` as a whole object instead of only its values, and both files assert that the worker's five projections exclude `icons/brand.png`.
- **Files modified:** `test/extension/toolbar-popup.test.js`, `test/extension/release-package.test.js`
- **Verification:** full suite green; `node scripts/package-release.js` produces a twelve-asset candidate.
- **Committed in:** `79863ae` (Task 2 commit)

**3. [Rule 2 - Missing critical] Committed the brand asset generator alongside the artwork**

- **Found during:** Task 2
- **Issue:** The plan listed `brand.png` and `promo.png` as artifacts but no way to produce them. Shipping binary artwork with no regeneration path leaves a shipped byte that cannot be reviewed, re-derived or adjusted without hand-editing a PNG — which sits badly in a project whose whole position is unminified, auditable, code-as-authored bytes, and which would make any future palette or sizing change unverifiable.
- **Fix:** Added `scripts/make-brand-assets.js`, a developer-only Node ESM script using `node:zlib` and nothing else. It adds no dependency, no package script, no bundler and no runtime change, sits outside `RELEASE_FILES` and outside `extension/`, and regenerating produces the committed bytes.
- **Files modified:** `scripts/make-brand-assets.js` (new)
- **Verification:** `node scripts/make-brand-assets.js` rewrites both PNGs; `git status` reports no change after a regeneration.
- **Committed in:** `79863ae` (Task 2 commit)
